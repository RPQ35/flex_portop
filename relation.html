Penjelasan Tahap 2NF (Second Normal Form)

Syarat 2NF adalah sudah berada dalam 1NF dan tidak memiliki ketergantungan parsial (atribut non-kunci hanya bergantung pada sebagian primary key). Pada tahap ini kita tentukan Composite Primary Key pada tabel detail dan memisahkan tabel menjadi 3 entitas awal: Tabel Nota, Tabel Barang, dan Tabel Detail_Transaksi.

Penjelasan Tahap 3NF (Third Normal Form)

Syarat 3NF adalah sudah berada dalam 2NF dan tidak ada ketergantungan transitif (atribut non-kunci bergantung pada atribut non-kunci lainnya). Pada tabel 2NF sebelumnya, Nama_Kasir bergantung pada ID_Kasir (bukan langsung pada No_Nota) dan Nama_Pelanggan bergantung pada ID_Pelanggan. Oleh karena itu, kita pisahkan entitas master tersebut menjadi Tabel Kasir dan Tabel Pelanggan yang berdiri sendiri.

Skrip SQL DDL & DML - POLNES Mart 
-- ==========================================
-- SKRIP SQL IMPLEMENTASI NORMALISASI POLNES MART
-- ==========================================

-- 1. PEMBUATAN TABEL MASTER KASIR
CREATE TABLE Kasir (
    ID_Kasir VARCHAR(10) PRIMARY KEY,
    Nama_Kasir VARCHAR(50) NOT NULL
);

-- 2. PEMBUATAN TABEL MASTER PELANGGAN
CREATE TABLE Pelanggan (
    ID_Pelanggan VARCHAR(10) PRIMARY KEY,
    Nama_Pelanggan VARCHAR(100) NOT NULL
);

-- 3. PEMBUATAN TABEL MASTER BARANG
CREATE TABLE Barang (
    Kode_Brg VARCHAR(10) PRIMARY KEY,
    Nama_Brg VARCHAR(100) NOT NULL,
    Harga DECIMAL(10,2) NOT NULL
);

-- 4. PEMBUATAN TABEL TRANSAKSI (NOTA)
CREATE TABLE Nota (
    No_Nota VARCHAR(10) PRIMARY KEY,
    Tanggal_Nota DATE NOT NULL,
    ID_Kasir VARCHAR(10),
    ID_Pelanggan VARCHAR(10),
    FOREIGN KEY (ID_Kasir) REFERENCES Kasir(ID_Kasir),
    FOREIGN KEY (ID_Pelanggan) REFERENCES Pelanggan(ID_Pelanggan)
);

-- 5. PEMBUATAN TABEL DETAIL TRANSAKSI
CREATE TABLE Detail_Transaksi (
    No_Nota VARCHAR(10),
    Kode_Brg VARCHAR(10),
    Qty INT NOT NULL,
    Sub_Total DECIMAL(10,2) NOT NULL,
    PRIMARY KEY (No_Nota, Kode_Brg),
    FOREIGN KEY (No_Nota) REFERENCES Nota(No_Nota),
    FOREIGN KEY (Kode_Brg) REFERENCES Barang(Kode_Brg)
);

Judul: Normalisasi Basis Data Relasional pada Sistem Transaksi Minimarket POLNES Mart

1. Pendahuluan

Dalam era digital saat ini, pencatatan transaksi berbasis manual menggunakan spreadsheet seringkali menimbulkan masalah redundansi data, anomali pembaharuan, serta inkonsistensi informasi. Kasus pada minimarket "POLNES Mart" yang baru beralih dari pencatatan manual ke sistem komputerisasi menunjukkan bahwa rekapitulasi harian dari struk belanja memiliki atribut berulang akibat penggunaan fitur Merge Cells pada format Excel (Bentuk Tidak Normal / UNF).

Tujuan dari praktikum ini adalah memahami dan menerapkan tahapan normalisasi basis data mulai dari Bentuk Tidak Normal (UNF), First Normal Form (1NF), Second Normal Form (2NF), hingga Third Normal Form (3NF) guna menghasilkan skema basis data relasional yang efisien, terstruktur, dan bebas anomali.

2. Bahan dan Metode

Waktu dan Tempat: Praktikum dilaksanakan pada bulan Oktober 2026 di Laboratorium Pemrograman dan Basis Data, Jurusan Teknologi Informasi, Politeknik Negeri Samarinda.

Metode Analisis: Metode yang digunakan adalah dekomposisi tabel bertahap berdasarkan kaidah normalisasi relasional Codd, dengan menganalisis ketergantungan fungsional (functional dependency), ketergantungan parsial, dan ketergantungan transitif pada data transaksi POLNES Mart.

4. Pembahasan

Berdasarkan hasil transformasi yang dilakukan, proses normalisasi sangat esensial untuk menghilangkan anomali insersi, penghapusan, dan modifikasi. Pada tahap 2NF, pemisahan dilakukan untuk mengatasi ketergantungan parsial dengan membentuk tabel terpisah untuk Nota, Barang, dan Detail Transaksi yang menggunakan Composite Primary Key `(No_Nota, Kode_Brg)`.

Selanjutnya pada tahap 3NF, ditemukan ketergantungan transitif di mana atribut `Nama_Kasir` dan `Nama_Pelanggan` bergantung pada atribut non-kunci masing-masing (`ID_Kasir` dan `ID_Pelanggan`). Pemisahan entitas master Kasir dan Pelanggan berhasil menghasilkan struktur basis data yang memenuhi standar Third Normal Form dan siap diimplementasikan ke dalam Sistem Manajemen Basis Data Relasional (RDBMS). Total belanja setiap nota tidak disimpan secara fisik melainkan dihitung secara dinamis sebagai derived attribute menggunakan fungsi agregasi SQL guna menjaga integritas data.
